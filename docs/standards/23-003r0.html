I.  Abstract

OGC API Standards define modular API building blocks to spatially enable Web APIs in a consistent way. The OpenAPI specification is used to define the API building blocks.

This Standard (“Part 3 — Publish/Subscribe”) defines how publish/subscribe protocols are used to asynchronously exchange CS API resources and their respective metadata and defined lifecycle events. It builds on the resource model and HTTP interface defined in OGC API — Connected Systems — Part 1 and on the dynamic data resource types defined in OGC API — Connected Systems — Part 2. It also extends the message and payload framework defined in OGC API — Pub/Sub by specifying the resource events, resource data messages, and protocol bindings specific to Connected Systems.

Part 3 provides a window into CS API and improves discoverability of resources as they become available for devices and systems already using popular pub/sub frameworks. Part 3 is intended to be deployed alongside a CS API HTTP server implementing the applicable requirements of Parts 1 and 2. It complements that server with asynchronous resource delivery and lifecycle notifications, using the same resource model and canonical URLs. Clients need not implement both HTTP and Pub/Sub interfaces.

Two categories of pub/sub messages are defined. Resource events are CloudEvents-formatted notifications that signal the creation, update, or deletion of any CS API resource; they identify the affected resource and may include optional JSON content as specified by the Resource Events requirements class. Resource data messages carry full resource representations using the native CS API encodings (JSON, SWE Common JSON, SWE Common Text, SWE Common Binary) and are intended for low-latency streaming of CS API resources, as well as for the registration of new resources from publishing clients.

CloudEvents provides a common, standardized notification envelope and does not require any cloud infrastructure. Resource Data Messages use native resource encodings without a CloudEvents envelope.

Protocol bindings define how these messages are exchanged over specific pub/sub transports. The common message requirements are independent of transport. MQTT is the first binding in this document and a primary worked example; its binding is a working draft. Additional bindings may be published separately and need not become official parts of this Standard to satisfy its applicable requirements. Implementing another binding does not require implementing MQTT.

1.  Scope

This Standard defines protocol bindings and message payload formats for using publish/subscribe (pub/sub) protocols with the OGC API — Connected Systems (CS API) framework. It extends OGC API — Connected Systems — Part 1 (resource model and HTTP interface) and OGC API — Connected Systems — Part 2 (dynamic data resource types) by enabling clients and servers to exchange CS API resources, lifecycle notifications, and streaming data asynchronously over pub/sub transports.

Specifically, Part 3 of the CS API defines:

  • Two main categories of pub/sub message payloads: Resource Events (CloudEvents-formatted lifecycle notifications) and Resource Data Messages (full resource representations carried in their native CS API encodings). A subtype of Resource Events Batch Resource Events (aggregated lifecycle notifications for high-volume cases), exists for cases where implementers require fewer message publications due to highly frequent lifecycle updates.

  • Protocol bindings that specify how these message categories are exchanged over particular pub/sub transports. This document defines the MQTT binding (v3.1.1 and v5). Additional bindings may be published separately, as extensions, or in future revisions; MQTT support is not a prerequisite for them.

  • Optional support for multiple resource representations, selected through separate pub/sub channels or an established content-negotiation mechanism supported by the transport.

The deployment model for this Part is a Pub/Sub interface associated with a CS API HTTP server implementing the applicable requirements of Parts 1 and 2. That server provides the API root and canonical resource and collection URLs used by the Pub/Sub interface. Pub/Sub components may operate on different hosts from the HTTP server; co-location is not required.

This Standard does not redefine resource models or HTTP operations defined in OGC API — Connected Systems — Part 1 or OGC API — Connected Systems — Part 2. It builds on the message-payload framework defined in OGC API — Pub/Sub — Part 1: Core, extending it for the Connected Systems domain.

OGC API — Connected Systems — Part 1 defines the feature resources that pub/sub channels in this Part exchange notifications and data about. OGC API — Connected Systems — Part 2 defines the dynamic data resource types (Observation, Command, Command Status, Command Result, System Event) that are most commonly streamed using the message categories defined here.

  • Clause 8.5, Batch Resource Events (Optional) defines an optional sub-class of Resource Events for CloudEvents-formatted aggregated lifecycle notifications, intended for high-volume cases such as observation streams.

7.  Overview

7.1.  General

The OGC API — Connected Systems (CS API) defines a unified set of resource types and HTTP operations for interacting with sensors, actuators, platforms, and the dynamic data they produce. OGC API — Connected Systems — Part 1 and OGC API — Connected Systems — Part 2 define those resource types and the synchronous HTTP interface.

In many Connected Systems use cases, however, the request/response pattern of HTTP is not the most efficient way to exchange data. Sensors produce observations continuously; actuators must accept commands with low latency; subscribers want to know about new resources as soon as they appear, without polling. For these cases, an asynchronous publish/subscribe interaction model is more appropriate.

This Part of the CS API specifies how pub/sub protocols deliver CS API resources and notifications about them asynchronously. The Pub/Sub interface is deployed alongside a CS API HTTP server and uses that server’s resource model, API root URL, and canonical resource and collection URLs. The HTTP interface provides retrieval of current resource state, while Pub/Sub provides asynchronous delivery. The components may run on different hosts and communicate through a separate broker.

7.2.  Message Categories

This Standard defines two primary categories of pub/sub messages, each addressing a different use case, plus a special-case sub-class of Resource Events for batched notifications:

  • Resource Events (Clause 8) are CloudEvents-formatted notifications of CS API resource lifecycle operations. They are emitted by the server when a resource is created, updated, or deleted. The notification identifies the affected resource by its absolute canonical URL in the associated CS API HTTP service. Its optional JSON content is governed by the Resource Events requirements class; consumers may use that content without retrieving the resource again. Optional inline content does not change the lifecycle-notification purpose or guarantee complete resource delivery.

  • Batch Resource Events (Clause 8.5) are a special case of Resource Events. They summarize a number of resource transactions of the same type that occurred on a single nested resource collection during a defined time window. They are intended primarily for high-frequency cases (for example, observation streams) where one event per transaction would be too verbose.

  • Resource Data Messages (Clause 9) carry complete resource representations in the server’s native CS API encodings (JSON, SWE Common JSON, SWE Common Text, SWE Common Binary, etc.). They are designed for low-latency streaming of observations, commands, command status, command results, and system events, as well as for “registration” use cases where a publishing client introduces new systems, datastreams, or controlstreams to the server.

CloudEvents provides a common, standardized envelope for lifecycle notifications and does not require any cloud infrastructure. Resource Data Messages use their native encodings without a CloudEvents envelope. Consumers use the message category appropriate to their needs: lifecycle changes through Resource Events, or complete resource delivery through Resource Data Messages.

The message categories are designed to be used together though implementations are only required to implement one primary category. A typical deployment exposes Resource Events for lifecycle notifications across resource types, Batch Resource Events for the highest-frequency nested collections, and Resource Data Messages for the dynamic data streams themselves.

7.3.  Protocol Bindings

The message categories above are protocol-agnostic. To exchange these messages over a specific pub/sub transport, this Standard defines protocol bindings: requirements classes that specify how the abstract message categories map onto the concrete operations (subscribe, publish, topic structure, content negotiation, flow control) of each pub/sub transport.

The common requirements do not assume any particular transport. MQTT (v3.1.1 and v5) is the first binding in this document and the primary worked example; see Clause 10.

A binding specifies how its transport satisfies each applicable common requirement, including resource identity, message content, publication and subscription behavior, and representation selection. Additional bindings are encouraged and may be published separately without becoming official parts of this Standard. Technical compliance depends on satisfying the applicable requirements. Neither official publication of the binding nor MQTT support is a prerequisite.

A binding that cannot satisfy a requirement applicable to its claimed capabilities needs adaptation or a defined conformance path through a standards extension or change. The requirement cannot simply be omitted. Each binding defines its transport-specific addressing and selection mechanisms while preserving the applicable common requirements.

NOTE:  The complete binding-independent conformance framework remains under development. Requirement-to-binding mappings, conformance dependencies and corresponding abstract tests remain to be specified and verified.

7.4.  Relationship to OGC API – Pub/Sub

This Standard extends OGC API — Pub/Sub — Part 1: Core by profiling its message-payload framework for the Connected Systems domain. The Resource Events requirements class inherits from the OGC API – Pub/Sub message-payload-cloudevents-json requirements class; the Batch Resource Events sub-class inherits from Resource Events.

Resource Data Messages do not inherit from any OGC API – Pub/Sub class, because the native CS API encodings (defined in OGC API — Connected Systems — Part 1 and OGC API — Connected Systems — Part 2) are not among the payload formats covered by OGC API – Pub/Sub Part 1.

8.1.  Overview

Resource events are a mechanism by which a CS API client can be notified of certain resource operations:

  • Resource creation (e.g. as initiated by an HTTP POST)

  • Resource update (e.g. as initiated by an HTTP PUT or PATCH)

  • Resource deletion (e.g. as initiated by an HTTP DELETE)

Listening for resource events can be done on a single resource or a valid collection of resources. The related topic will closely resemble a valid REST endpoint from parts 1 & 2.

Resource Events are encoded as CloudEvents v1.0 messages using the JSON Event Format.

This lifecycle notification includes the complete Part 1 GeoJSON System representation as optional data. The example uses the resource content from the Part 1 thermometer example without adding or moving fields. In particular, the resource’s name and description remain inside its GeoJSON properties object; they are not copied to the top level of data to satisfy summary-specific conventions.

8.3.  Resource identity and the associated HTTP server

The source attribute identifies the associated CS API HTTP server’s resource context through its absolute API root URL. The subject attribute identifies the affected resource through its absolute canonical URL, and resourceparent identifies its direct parent through that parent’s absolute canonical URL. These identifiers come from the CS API resource model and HTTP interface; they are not broker addresses or channel names.

These URLs serve as stable identifiers across publisher restarts, broker migrations, and channel-address changes. A deletion event retains the deleted resource’s canonical URL and its direct parent’s canonical URL immediately before deletion. Retaining an identifier does not guarantee that an HTTP request will still retrieve a representation after deletion.

8.5.1.  Overview

Batch Resource Events are a special case of the per-resource Resource Events defined above, intended for cases where publishing one event per resource transaction is impractical — for example, high-bandwidth datastreams and control streams where the per-resource event volume would overwhelm subscribers.

A Batch Resource Event is a CloudEvents v1.0 message that summarizes a number of resource transactions of a single type (create, update, or delete) that occurred on a single nested resource collection during a defined time window. It does not carry the individual resources or their identifiers; only their count, the event type, and the time window.

Implementing this requirements class is optional. Since it inherits from the Resource Events requirements class, conformance to Batch Resource Events requires conformance to Resource Events.

Batch Resource Events are not intended for low-frequency resource collections such as the canonical collections of systems, deployments, procedures, properties, or the per-system collections of subsystems, datastreams, controlstreams, sampling features, or deployments. For those collections, per-resource Resource Events are sufficient and avoid the additional complexity of batch aggregation. The specific resource collections for which Batch Resource Events MAY be published are enumerated in /req/resource-events/batch-events/allowed-collections.

8.5.2.  Message Format

A Batch Resource Event uses the same CloudEvents v1.0 JSON envelope as a regular Resource Event (see Table 1) with a few key differences:

  • The subject attribute identifies a nested resource collection (resources endpoint) that the batch summarizes, rather than an individual resource. The collection is nested under exactly one parent resource (e.g. observations under a single datastream). Top-level resource collections and collections that span multiple parent resources are not allowed; the permitted collections are enumerated in /req/resource-events/batch-events/allowed-collections.

  • The data member is required and carries summary statistics for the batched operations.

9.1.  Overview

Resource Data Messages allow CS API resources to be exchanged through publish/subscribe channels as their native representations rather than as Resource Events. They are designed for low-latency, high-volume streaming of dynamic data — observations, commands, command status updates, command results, and system events — as well as for “registration” use cases where a publishing client introduces new systems, datastreams, or controlstreams to the server.

A Resource Data Message carries the resource itself, not a notification about it. Subscribers receive the full resource representation; consumers do not need to make a follow-up request to retrieve the resource by URL.

Resource Data Messages are restricted in two important ways:

  • Only specific CS API resource types are eligible (see Table 6). The Resource Events class remains the appropriate mechanism for lifecycle notifications of other resource types (deployments, procedures, properties, sampling features, etc.).

  • Resource deletions are never signaled by Resource Data Messages. Deletions are conveyed only by Resource Events.

Implementing this requirements class is optional. A server MAY implement Resource Data Messages without implementing Resource Events, or vice versa, or both, or neither.

9.2.  Message Format

A Resource Data Message carries a complete representation of a single CS API resource. Unlike Resource Events and Batch Resource Events, the message payload is not wrapped in a CloudEvents envelope — it is the resource representation itself, encoded in one of the formats supported by the server.

CommandOGC API — Connected Systems — Part 2Sending commands to actuators or controllable systems.
Command StatusOGC API — Connected Systems — Part 2Streaming command status transitions.
Command ResultOGC API — Connected Systems — Part 2Streaming command results.
System EventOGC API — Connected Systems — Part 2Streaming system-emitted events.

ControlstreamOGC API — Connected Systems — Part 2Registering a new controlstream associated with a system.

Resource Data Messages support both server-to-client and client-to-server message flows. The publish authority for each resource type and channel is defined by the protocol binding (for example, the MQTT Transport requirements class); the message-format class defined here is silent on who may publish.

The encoding used for a given Resource Data Message is one of the formats supported by the server for the resource type being carried, as defined by the encoding requirements classes of OGC API — Connected Systems — Part 1, OGC API — Connected Systems — Part 2, or future Parts. 9.4.1.  Overview

Support for multiple representations of a resource-data stream is optional. Each offered stream provides at least one permitted media type under /req/resource-data-messages/representation-offering. An implementation offering several representations provides explicit selection through separate channels or, where supported, an established transport content-negotiation mechanism.

The binding defines the concrete mechanism, and the service description tells clients which representations are offered and how to select them. Supporting an encoding elsewhere in the API does not automatically offer it through Pub/Sub. Implementations may optimize when they produce representations, but preserve the advertised channel behavior and negotiated selections. Subscriber-count detection is not required.

Content-type metadata identifies a message’s representation; it does not itself negotiate a representation. For example, MQTT’s Content Type property describes the published payload. By contrast, SIP event subscriptions use Accept in SUBSCRIBE to specify permitted NOTIFY body formats (RFC 6665, section 3.1.3). This is a negotiation precedent, not a definition of a CS API SIP binding.

For example, a service may advertise an Observation stream as application/json only. A service offering both application/json and application/swe+binary may advertise separate channels for the two representations. A client selects the advertised channel for its desired representation; support for another encoding on an HTTP endpoint does not add a Pub/Sub offering.

Bindings may use the normalized format-name convention below for channel selection. Channel syntax remains a binding responsibility. Normalization discards media-type parameters and can collapse distinct types to the same name, so the service description and selection mechanism must still distinguish every offered representation unambiguously.

  • Wildcard subscription support;

  • Error reporting behavior.

D

Settings shared by multiple topics MAY be described once, provided their applicability is clear.

The associated HTTP server provides resource URLs, schemas and resource retrieval. The MQTT broker may be hosted separately.

The service description may use AsyncAPI or another format that expresses the required information.

10.3.  Topic Structure

10.3.1.  Construction Rule

MQTT topics begin with {nodeId}, followed by a resource path using the collection names defined in OGC API — Connected Systems — Part 1 and OGC API — Connected Systems — Part 2.

A designated topic follows the resource’s full ownership hierarchy. For Resource Data Messages, it also depends on the representation (see Clause 10.5.2). Subsystems appear beneath their parent systems, and resources owned by a subsystem appear beneath that subsystem’s full path. For example, node1/systems/1/subsystems/7/datastreams/42 identifies DataStream 42 owned by Subsystem 7 of System 1.

The node identifier distinguishes CS API HTTP servers sharing a broker. It occupies one topic level and contains no /, + or # characters.

Table 8 — MQTT Topic Placeholders

PlaceholderExpands to
{nodeId}The advertised node identifier (a single topic level).
{systemPath}The full system path: systems/{id}, followed by /subsystems/{id} for each subsystem level. Examples: systems/134, systems/134/subsystems/7.
{deploymentPath}The full deployment path: deployments/{id}, followed by /subdeployments/{id} for each subdeployment level.
{id}The resource’s local identifier in the CS API HTTP server, mapped to one topic level (see /req/mqtt/topic-mapping).

A topic is valid for a resource or collection when its path follows the resource associations defined in OGC API — Connected Systems — Part 1 and OGC API — Connected Systems — Part 2: the first collection is at the API root, each later collection represents an association of the preceding resource, and each identifier names a member of its collection.

Servers may also publish copies on advertised additional topics that follow these associations, subject to /req/mqtt/topic-mapping and /req/mqtt/data-messages. Publication on each message’s designated topic remains required, even when copies are published on additional topics.

Requirement 20

Identifier/req/mqtt/topic-mapping
Included inRequirements class 5: /req/mqtt
A

The implementation SHALL use the topic templates in Table 9 and Table 12 for the resource types and message categories it offers over this binding.

B

The advertised {nodeId} SHALL be a nonempty, single MQTT topic level that contains no topic level separator (/) and no wildcard character (+, #). It SHALL be unique to the associated CS API HTTP server within the broker.

C

Resource identifiers SHALL occupy one MQTT topic level each. The service description SHALL specify a reversible mapping from HTTP path identifiers to topic levels. The mapping SHALL prevent identifier values from introducing topic level separators, wildcard characters or the :data marker, and SHALL distinguish a literal percent escape from the character that escape represents.

The implementation SHALL publish each Resource Event on its designated topic: the topic of the affected resource’s most nested path, with {systemPath} and {deploymentPath} expanded to the full chain of parent resources. The {nodeId}/systems/{id} topic SHALL carry events of top-level systems only, and the {nodeId}/deployments/{id} topic SHALL carry events of top-level deployments only.

E

When Batch Resource Events are offered, the implementation SHALL publish each Batch Resource Event on the designated topic of the summarized collection, formed by removing the final {id} level from the corresponding Resource Event topic.

F

The implementation SHOULD publish each Resource Event and Batch Resource Event only on its designated topic. It MAY also publish it on additional topics that are valid for the resource or collection, as described in Clause 10.3, except that it SHALL NOT publish a Batch Resource Event on a topic of a top-level collection, and SHALL NOT publish any message on a top-level Observations or Commands topic ({nodeId}/observations/…, {nodeId}/observations:data, {nodeId}/commands/… or {nodeId}/commands:data). Every copy SHALL carry the same CloudEvents source and id. The service description SHALL identify any additional topics on which copies are published.

G

The topic SHALL NOT replace the absolute canonical resource URL required in the CloudEvents subject and resourceparent attributes. Clients SHALL NOT be required to derive resource identity from a topic.

H

The identifier in a Resource Event topic SHALL identify the affected resource in the associated CS API HTTP server. A value that the HTTP server does not use as the resource identifier, such as an observation timestamp, SHALL NOT be substituted for it.

10.4.3.  Batch Resource Event Topics

This subsection applies when Batch Resource Events are offered over MQTT.

A Batch Resource Event uses the corresponding collection topic, formed by removing the final resource identifier from the Resource Event topic. For example, a batch for DataStream 145’s observations uses node1/systems/134/datastreams/145/observations.

Each batch notification is one structured CloudEvent with media type application/cloudevents+json, as required by /req/mqtt/event-messages. It does not use the CloudEvents JSON batch format (application/cloudevents-batch+json).

The filter …/observations/+ matches individual observation events. The filter …/observations/# also matches batch notifications on the collection topic.

10.4.4.  Deployments

A Deployment may involve multiple systems (see OGC API — Connected Systems — Part 1). Its designated topic follows the deployment hierarchy under {nodeId}/deployments/…, with subdeployments nested beneath their parent deployment. The HTTP endpoint {api_root}/systems/{sysId}/deployments provides a filtered view of those associations.

To receive Deployment Resource Events, subscribe to {nodeId}/deployments/#. Selecting events relevant to a particular system requires deployment membership information. When the optional event data includes that information, clients can interpret it using the advertised media type and schema. Otherwise, clients can retrieve the deployment through its canonical HTTP URL while it remains available. Previously retrieved membership information can help clients process later updates or deletions. A deletion event may omit membership information, and the deleted resource may no longer be retrievable.

Servers MAY also publish copies under {nodeId}/systems/{id}/deployments/{id} for each associated system (see Clause 10.3).

Example — Using cached membership to process a Deployment deletion

A client subscribes to node1/deployments/#. It has previously retrieved https://example.org/api/systems/134/deployments and recorded that the top-level Deployment https://example.org/api/deployments/53 involves System 134. In this example, that association remains unchanged until Deployment 53 is deleted. The server then publishes the following event on node1/deployments/53:

 

{
  "specversion": "1.0",
  "id": "deployment-53-deleted-01",
  "source": "https://example.org/api",
  "type": "org.ogc.api.csapi.deployment.delete",
  "subject": "https://example.org/api/deployments/53",
  "time": "2026-10-08T16:02:11Z"
}

The client matches subject to its cached membership and removes Deployment 53 from its local view of System 134’s deployments. It does not need to retrieve the deleted resource. A client without that membership information cannot determine from this event alone whether Deployment 53 involved System 134.

10.4.5.  Resource Events and System Events

A Resource Event notifies clients that an API resource was created, updated or deleted. Its time records the API operation.

A System Event, defined in OGC API — Connected Systems — Part 2, is a stored resource describing an occurrence such as calibration, repair or deployment. Its time records when that occurrence happened.

Creating a System Event therefore produces a Resource Event of type org.ogc.api.csapi.systemevent.create on {nodeId}/{systemPath}/events/{id}. This binding does not require a corresponding System Event record for every resource change.

D

E

For binary representations, the service description SHALL identify the framing, how to retrieve the schema, and the schema version or other means of selecting the correct schema. The implementation SHALL carry the representation bytes unchanged. It SHALL NOT convert them to a JSON string or Base64 wrapper unless that wrapper is part of the advertised representation.

This binding does not provide a general mechanism for identifying duplicate Resource Data Messages. Publishing each representation only on its designated topic avoids duplicates caused by additional-topic publication.

A receiving service may reject MQTT 5.0 publications that omit Content Type. This check requires knowing the publisher’s MQTT version: messages published using MQTT 3.1.1 have no Content Type, even when received by an MQTT 5.0 subscriber.

10.6.  Subscriptions

This section outlines how a properly configured service should handle subscriptions.

Requirement 24

Identifier/req/mqtt/subscriptions
Included inRequirements class 5: /req/mqtt
A

The implementation SHALL accept authorized subscriptions to advertised topics and topic filters, subject to declared capacity limits. It SHALL report unsuccessful subscriptions using the applicable MQTT acknowledgement.

B

Topic filters SHALL follow the wildcard rules of the MQTT version in use. An accepted filter SHALL cover every authorized matching topic offered by the service, including topics for resources created later. The service description SHALL declare restrictions on wildcard subscriptions to Resource Data topics.

C

The service SHALL enforce resource access control for exact topics, topic filters, retained messages and resumed sessions. Users SHALL NOT receive resource information through MQTT that they are not authorized to retrieve through the associated CS API HTTP server.

A filter ending in # can match both Resource Event and Resource Data topics. Use a more specific filter to select one category. Retained or queued messages may describe an earlier resource state.

10.7.  Client Publication

Services may allow clients to publish data on appropriate topics unless it is disallowed as in the case of Resource Events.

Requirement 25

Identifier/req/mqtt/ingestion
Included inRequirements class 5: /req/mqtt
A

If client publication is offered, the service SHALL advertise the writable Resource Data topics and the CS API create operation each performs. Before accepting an operation, it SHALL validate authorization, the representation and the target collection. Each client publication SHALL be a separate create operation; clients SHALL publish each resource on one topic only. Users SHALL NOT create resources through MQTT that they are not authorized to create through the associated CS API HTTP server.

B

Client publication SHALL NOT authorize deletion or other CS API operations. The service SHALL reject malformed, unsupported or unauthorized publications according to its advertised error behavior.

C

The deployment SHALL prevent unvalidated client input from reaching subscribers as accepted Resource Data messages. When input and output share a topic, the broker or an integration layer SHALL validate input before distribution and prevent republishing loops.

D

The service description SHALL distinguish MQTT delivery acknowledgement, CS API operation acceptance and command execution status. For asynchronous acceptance or rejection reports, it SHALL describe the topic, correlation and payload.

Clients may publish to advertised writable Resource Data topics, such as node1/systems/134/datastreams/145/observations:data. Client publication is optional.

When clients and the server publish on the same topic, the broker or an integration layer validates client input before forwarding it to subscribers. Separate input topics require an extension. This binding does not define a general request/reply protocol.

10.8.  Delivery Behavior

This section defines what a service should declare about QoS, session persistence, retained messages and message size.

Requirement 26

Identifier/req/mqtt/delivery
Included inRequirements class 5: /req/mqtt
A

The service description SHALL state publication QoS, supported subscription QoS levels, session expiry or persistence policy, and any ordering or replay guarantees beyond MQTT. It SHALL NOT claim that transport QoS alone guarantees exactly-once resource creation or command execution.

B

The service description SHALL state the retained-message behavior of Resource Data topics. A retained command SHALL NOT execute as a new command when a service reconnects. If retained state snapshots are offered, the description SHALL explain how they are distinguished from new observations or commands.

C

The service SHALL publish complete representations within its advertised message-size limits. Larger representations SHALL be rejected or handled by a separately described extension. This binding does not define fragmentation.

MQTT subscriptions select messages by topic. This binding does not define payload or property filters, rate limiting or sampling. The following optional MQTT 5.0 features help control delivery:

FeatureEffect
Receive MaximumLimits unacknowledged QoS 1 and QoS 2 messages; it does not limit QoS 0 traffic.
